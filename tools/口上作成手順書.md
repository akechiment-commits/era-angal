## 1. 作業対象ファイルの場所

### キャラごとに存在するファイル（3種）

```
ERB/CHAR/CHAR_NN_名前.ERB        ← ベースERB（行事・挨拶・エンディング等、約100スロ）
ERB/CHAR/CHAR_NN_名前_COM.ERB    ← COMERBメイン（936スロ、主作業）
CSV/CharaNN_名前.csv              ← 素質定義（キャラのパラメータ）
```

`NN` はキャラ番号（01〜71）。

### 全キャラ共有ファイル（口上関連）

```
ERB/KOUJO/KOJO_HOURAI_蓬莱薬口上.ERB  ← 蓬莱の薬(不老不死)使用時の口上を全キャラ集約（@HOURAI_KOJO_NN）
```

※2026-05-27に各CHAR_*_COM.ERBから蓬莱口上を切り出してここへ集約。新キャラの蓬莱口上はここに追加する（詳細はステップ2の「蓬莱の薬の注意」）。

### 参照資料ファイル（キャラ別）

優先度順に読む。

| 優先度 | ファイル | 場所 | 内容 |
|--------|----------|------|------|
| ★必須 | `{名前}_v3.txt` | `tools/v3prompt/` | キャラプロファイル＋会話パターン（最新版） |
| ★必須 | `{名前}.txt` | `tools/output/` | 原作セリフ全文（口調確認の一次資料） |
| ★必須 | `{名前}_分析.txt` | `tools/output/` | 語尾・口癖・一人称などの定量分析 |
| 状況次第 | `{名前}_転校生.txt` | `tools/output/` | 転校生（プレイヤー）への言及・呼びかけ方の抽出 |

## 2. ステップ0: 設定.txt を作る（着手前に明智さんの確認を取る）

### やること

1. `tools/v3prompt/prompt_{名前}_v3.txt` と `tools/output/{名前}.txt`、
   `{名前}_分析.txt` を読んで原作セリフ・性格を把握する
   - ★**「自称」と「実態」を必ず分離する**（ましろセッションの学び）。
     キャラの自己卑下・ネタ設定（例:「私は馬鹿だ」）を額面どおり
     受け取らない。原作シナリオで裏取りし、実態と違うなら実態を採る。
     例: 日滝ましろは「自称馬鹿」だがシナリオ2704で問題集を全問正解、
     「運動も勉強もできる」と評される＝**勉強は苦手ではない**。
     v3の「思考単純」だけ見て勉強苦手と書くと手戻りになる（口上9箇所修正）。
2. **既存 CSV (`CSV/Chara{NN}_{名前}.csv`) の素質はいじらない**
   - 既に上流で決まっているので尊重する
   - 設定.txt には参考情報として既存素質一覧を記載するだけ
3. **新規に追加すべき素質候補があれば「別枠の追加提案」として書く**
   - 原則: **迷ったら付けない**（追加0個でも可）
   - 「キャラがその素質の人物に見えるか」で判断
   - `tools/talent_list.txt` を参照
   - 明智さんの判断で追加するか/しないかを決める
4. 紹介文（一人称・口調・性格核・人間関係・主人公呼称）をまとめる
5. 明智さんに見せて確認をもらう

### 設定.txt の保存先

```
tools/CHAR_NN_{名前}_設定.txt
```
（リポジトリ内に保存して git 管理対象にする）

## 3. ステップ1: ベースERBを埋める（約100スロ）

### 書くセクション

| セクション | 内容 |
|-----------|------|
| `@CHAR_FIRST_DIALOG_NN` | 初回出会い |
| `@CHAR_REPEAT_DIALOG_NN` | 毎回挨拶 |
| `@CHAR_MORNING_GREETING_NN` | 朝の挨拶 |
| `@CHAR_REST_NN` | 休憩選択時の口上 |
| `@CHAR_LUNCH_NN` | 昼休み |
| `@CHAR_PARTNER_DIALOG_NN` | パートナー選択時（★2026-05-28拡張：恋人RAND3＋通常RAND3＝6スロ） |
| `@CHAR_SESSION_END_NN` | セッション終了（★2026-05-28拡張：18スロ。`IF TFLAG:44`(ウフフ突入)→`IF BASE:TARGET:0 <= 750`(低体力/疲労)で分岐。①ウフフ低体力[恋人3,通常3]②ウフフ通常体力[恋人3,通常3]③ウフフなし=従来[恋人3,通常3]。体力はパートナー(TARGET)・固定値750以下で疲労困憊セリフ） |
| `@CHAR_SPORTS_FESTIVAL_NN` | 体育祭 |
| `@CHAR_CULTURE_FESTIVAL_NN` | 文化祭 |
| `@CHAR_EXAM_BEFORE_NN` / `@CHAR_EXAM_RESULT_NN` | 試験前後 |
| `@ENDING_MARRIAGE_NN` / `@ENDING_GRADUATE_NN` | エンディング |
| `@CHAR_MILK_NN` | 搾乳 |
| `@CHAR_FUTA_EJAC_NN` | ふたなり射精 |

### 書き方の注意

- **ファイル読み書きはPythonで cp932 + CRLF**（Editツール使用禁止）
- ★`@CHAR_*` の出現回数は**ファイルによって違う**（ましろセッションの学び）。
  二重定義のファイルもあれば、各セクション1回だけのファイルもある
  （CHAR_67 日滝ましろは全セクション1回ずつだった）。**まず grep で
  出現回数を確認**し、1回なら1回目、2回定義なら2回目に書く:

```python
import re
matches = list(re.finditer(rf'@{セクション名}\b', content))
start = matches[-1].start()  # 最後の出現＝1回なら1回目、2回なら2回目で安全
```

### ★エンディング口上の鉄則（卒業EN ⇔ 結婚EN の差・山場の長文化）

分岐元: `ERB/ENDING_エンディング・ゲーム終了判定.ERB` の `@ENDING_PLAYER`（`IF TALENT:A:89` ＝妻素質で呼び分け）。

- **`@ENDING_MARRIAGE_NN`（結婚エンド）** … `TALENT:89`（妻）持ち＝**相愛で結ばれた**相手に流れる。「ふたりで生きていく／これからが本当の始まり」と**結ばれて一緒になる**基調で書く。
- **`@ENDING_GRADUATE_NN`（卒業エンド）** … 相愛/結婚に**至らなかった**相手を見送る**別れエンド**（汎用エピローグ `@ENDING_GRADUATE_DEFAULT` も『同じ制服でここに立つことはもうない／別れ際に振り返り静かに微笑んだ』と完全に別れ基調）。
  - ❌ **禁止**：「ずっと一緒にいて」「そばにいて」「隣で見てて」「これからもパートナーでいて」等の **“結婚EN調＝交際継続”の締め**。卒業ENでこれを書くと分岐の意味と矛盾する（2026-05-28 に22キャラ分を一括是正した実例あり）。
  - ✅ **正解**：感謝 ＋ 旅立ち（＝転校生が学校を出ていく）＋「離れても忘れない／お元気で／またどこかで会おう」。**片想いの余韻**（「ほんとはずっと一緒にいたかった…なんて、言わないでおく」等）はキャラ性に応じて残してよい（＝相愛未満を見送る切なさ）。

- **山場は必ず長文化する**：山場（プロポーズ・エンゲージリング・**結婚EN**・**卒業EN**・告白26／相手からのファーストキス25・グッド初回妊娠/出産）は、短い1〜2文で済ませず**十分なボリューム**にする。固有エピソード（部活・渾名・出会いの場面）を盛り込んで情緒を作ること。各 `@` 関数の直上に `; ★山場: 十分なボリュームの口上にすること` とコメントを置く運用。
  - **★字数目安（2026-05-29 確定）**：**山場＝200字程度**（プロポーズ・エンゲージ・告白成功/相手から告白26・相手からキス25・グッド初回妊娠/出産）、**エンディング＝400字程度**（結婚EN・卒業EN）。※あくまで目安。情緒が乗るなら多少前後してよい（実装例：CHAR_14ことり＝山場209〜280字／EN396〜399字）。`%CALLNAME:PLAYER%` の展開分は字数に含めず本文で測る。

### ステップ2: 純愛コミュ（約215スロ）

```
COM300〜325（211スロ）
※蓬莱の薬(@HOURAI_KOJO 4スロ)は専用ERBへ移設済み（下記「蓬莱の薬の注意」参照）
```

**★会話（COM301）は RAND:10 に拡張済み（2026-05-24）**:
- 最も使用頻度が高く個性が出るコマンドなので、恋人/親密/通常 各10＋初回1＝31枠
  （旧16枠から+15）。テンプレート・未実装45体・やこ(52)に適用済み。
- 他の実装済み24体は旧RAND:5(16枠)のまま。今後個別に拡張する場合あり。
  （28星海こよいは2026-05-28にRAND:5→RAND:10へ拡張済み＝渡し分の部分実装を完成させた）
- ※RAND:10で空きスロを残すとゲームが空セリフを引くため、構造拡張と本文記入は必ずセット。

**★会話には失敗分岐がある（COMF301で低確率の失敗判定）**:
- 失敗時は好感度・従順が下がる → 突き放し/機嫌を損ねた反応を書く。
- テンプレに失敗分岐（`IF TFLAG:18 == -1` → 恋人失敗1 + 失敗1）あり。必ず埋める。
- ※旧テンプレ由来のキャラは会話の失敗分岐を持たない個体が多い（失敗時に成功
  セリフが出る不整合）。新規実装時は会話の失敗も忘れず記入。

**★純愛コマンドに「原作セリフそのままコピー」を混ぜる（みなづき47で確立・2026-05-25）**:
- 会話(COM301)・スキンシップ(COM303)・まったり(COM304)等に、原作セリフを
  一字一句そのまま(verbatim)混ぜると「らしさ」が増す。`tools/output/{名前}.txt` /
  `{名前}_転校生.txt` から句読点・♪・波ダッシュまで原文どおりコピー。
- 分量は各コマンド・各層に **1〜2本ぐらい**。★ふさわしい文が無ければ無理に入れない（0本可）★。
- ★コマンドの文脈に合うものを選ぶ★（くすぐったい/頭撫で/抱きしめ→スキンシップ、
  くつろぎ→まったり、からかい/雑談→会話）。場面ミスマッチは厳禁。
- ★一対一で成立しないセリフは入れない★（同席キャラ前提・場面依存はNG。例：
  「翻訳すると、みづちゃんは…」は姉が同席する前提＝二人きりの会話では不自然）。
- 自作と原作でテーマが被ったら被る自作スロットを原作で上書きして一本化する。
- 技術注意：原作txtはUTF-8、ERBはcp932。波ダッシュは U+FF5E(～) に正規化して
  照合・書き込み（cp932は U+301C のencodeに失敗しうる）。半角~(U+007E)は厳禁。
- ※詳細な決まりは `引き継ぎ書_v23.txt` v24セクション 学びA を参照。

**蓬莱の薬（@HOURAI_KOJO）の注意（★2026-05-27 構造変更）**:
- 蓬莱の薬の口上は **専用ファイル `ERB/KOUJO/KOJO_HOURAI_蓬莱薬口上.ERB` に集約**した。
  以前は各 `CHAR_NN_名前_COM.ERB` の中（COM310調合直後＋後半の2箇所）に置かれており、
  その無条件 RETURN がプレイ口上(COM0〜191)を到達不能にしてバグの原因になっていたため、
  全キャラ分をこの専用ERBへ移設した。**CHAR側COM_ERBにはもう蓬莱口上は無い**。
- **新キャラの蓬莱口上は、この専用ERBに `@HOURAI_KOJO_<キャラ番号>` を追加して書く**。
  ファイル末尾の `@HOURAI_KOJO_0` が空欄の雛形なので、複製して番号を付け替えて使う。
- 呼び出しは従来どおり COMF310（調合）の `TRYCCALLFORM HOURAI_KOJO_{NO:TARGET}`。
  Emueraは関数を全ERB横断で名前解決するので、ファイルが別でも問題なく呼ばれる。
- ※プレイ口上・会話口上は引き続き各CHARの `@KOJO_MESSAGE_COM_<番号>` 側に書く（蓬莱だけ別ファイル）。

### ★視点（攻め／受け）判定の鉄則★（ほとりセッションで誤判あり・最重要）

- **★★視点要注意COMは必ず注釈に `;▼【視点】` を付ける（黒森すずセッションで確立）★★**:
  視点を取り違えやすいCOMは、該当COM見出しの直下に
  `;▼【視点】キャラ攻め/受け/奉仕＝<行為主体と相手>` の一行を必ず置く。
  こうすれば `grep ';▼'` で危険COMを一覧でき、`;※` 詳細に埋もれて読み飛ばす事故を防げる。
  **▼必須の判定基準**（いずれか該当）:
  1. 名前が紛らわしい（`〜する`/`〜させる`/`〜される`で行為主体が逆に読める）
     例: COM4フェラする・COM380＝逆フェラでキャラ受け／COM130-132される＝主語はキャラで攻め
  2. 相手は女性＝助手/他の女子（女性器・胸・膣挿入・ペニバンなど女性同士でしか成立しない行為）
     例: COM61/63/200/203/192/193/194/195/196/381（★193/194/195/196/381は2026-05-29に女性限定へ）
  3. ふたなり逆行為でキャラ受け 例: COM67/191（※196も受けだが相手は女子＝ペニバン装着者）
  4. キャラが見る/命じる/煽る側 例: COM56/205
  5. 奉仕の方向や人数が紛らわしい 例: COM35/37/38/39/66/68/80/201
  → 明白な受け本番（COM20正常位等、名前と視点が一致）には付けない（▼を「要注意」の信号として温存）。
  ※CHAR_62黒森すずのCOMファイルに34COM分の `;▼【視点】` を付与済み（参照実装）。
- **最終判断は必ず該当COM直上の注釈を一次情報にする**。注釈は `;※` だけでなく
  **`;▼` で書かれているCOMもある**（深鳥ふみセッションの学び）。`;※` だけを
  grepすると `;▼` のみのCOMを取りこぼし、視点を逆に書く事故になる。
  **必ず `;※` と `;▼` の両方を拾うこと**。実際に全実装キャラで逆になっていた例:
  - **COM205 自慰見せつけ**（注釈 `;▼ プレイヤーがパートナーに自慰を見せる`）＝
    **キャラは見る側**（自分が自慰して見せるのは誤り）。
  - **COM67 足コキ**（注釈 `;▼ ふたなりのパートナーに対してプレイヤーが足コキする`）＝
    **キャラは受け**（自分が足コキするのは誤り）。
- **★女性器用コマンドは相手＝転校生になり得ない（COM61クンニと同型）★**:
  **COM203 クスコ**（女性器に挿入する診察器具）は、転校生が常に男性ゆえ
  **相手は助手か他の女子生徒（女性同士の行為）、キャラが使う側**。
  「転校生にクスコを使う」「キャラ自身がクスコされる」はどちらも誤り
  （キャラ自身が受けるのは COM110 クスコの方）。全COM203注釈に
  「クスコは女性器用→相手は女子生徒（女性同士の行為）」のクラリファイを追記済み。
- ★視点を直すときも**説明調にしない＝実演型で**（明智さん指摘）。「あなたが〜するの？」と
  状況を述べるのでなく、見ている眺め・身体感覚・相手や自分の反応を書く。
- コマンド名の「〜する／〜させる」は攻め受けの**当てにならない**
  （`手淫する`でもキャラが受け側のことがある）。

## 7. ファイルの読み書き

### 必須: Python で cp932 + CRLF

```python
# 読み込み
with open('ERB/CHAR/CHAR_NN_名前_COM.ERB', 'rb') as f:
    content = f.read().decode('cp932')

# 書き込み（★encodeを先に変数へ確定してから開く★）
data = content.encode('cp932')   # ここで失敗してもファイルは無傷
with open('ERB/CHAR/CHAR_NN_名前_COM.ERB', 'wb') as f:
    f.write(data)
```

- **Edit ツール使用禁止**（UTF-8で上書きされて文字化けする）
- ★**`open(...,'wb').write(text.encode('cp932'))` と1行で書くな**★（CHAR55で全損事故）。
  `open('wb')` はファイルを**先に0バイトへ切り詰めて**から書く。encodeが
  cp932非対応文字で失敗すると、write前に例外→**ファイルが空のまま破壊される**。
  必ず上記のように **encodeを変数に確定してから** `with open('wb')` で書くこと。
  さらに fill リストの各行に事前チェックを入れると安全:
  ```python
  for s in lines:
      try: s.encode('cp932')
      except UnicodeEncodeError as e: raise SystemExit(f'cp932不可: {s}')
  ```
- ★cp932非対応漢字に注意★: 「剝」(U+525D) は cp932 不可 →「剥」(U+5265) を使う
  （剥く/剥がす等。半角~と同じく見た目が紛らわしい別字）。
- 波線は `〜`（U+301C）推奨。ただし `〜`(U+301C) も `～`(U+FF5E) も
  cp932 では同一バイト `0x8160` になり機能差はない（既存ファイルは 0x8160）。
  半角 `~`(U+007E/0x7E) だけは別物なので使わない。
- ★例外: 蓬莱専用ERB `ERB/KOUJO/KOJO_HOURAI_蓬莱薬口上.ERB` は**改行が LF**★
  （CHAR側ERBはCRLF）。`@HOURAI_KOJO_NN`(空4枠・TFLAG:91の0-3)を埋めるときは
  このファイルだけ LF を維持する（`assert '\r\n' not in t` で混入を防ぐ）。

### 運用上の恒久注意（過去ログから残す分）

- **master が並行開発で force-update され得る**：作業ブランチを master へ反映する際、
  `git push --force` でブランチ内容を上書きするのは厳禁（master側の並行作業を破壊する）。
  必ず `git merge` で統合し、競合（多くは本ロスターのみ）は両系統のエントリを残して解決する。
  push が rejected されたら `git fetch` → 再マージ → push。
- **Emuera は関数を `@ラベル名` で解決する（ファイル名でなく）**：同一フォルダ内に同名ラベルが
  2つあると重複定義エラー／呼び出し不定になる。新規ファイル追加時はラベル衝突に注意
  （38 クー・カロアでファイル名衝突＝同一 `@..._38` 二重定義の事故があった）。
